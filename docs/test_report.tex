\section{Test plan}

\subsection{Objectives}

\begin{enumerate}
  \item Confirm that every feature in the requirements works as specified.
  \item Confirm that every \emph{refusal} works: invalid input, full or started events, duplicate
        registrations, venue clashes and access by the wrong role are rejected and change nothing.
  \item Protect the profiling optimisation: the reports must return exactly the same numbers after
        the query rewrite and with or without indexes.
  \item Make tests fast and repeatable so they can be run before every commit.
\end{enumerate}

\subsection{Scope}

\begin{description}
  \item[In scope] All routes in \code{auth}, \code{events} and \code{admin}; the helper functions
        \code{find_clash}, \code{percent} and the three report functions; database constraints that
        the code relies on (unique registrations, cascade delete).
  \item[Out of scope for automation] Visual layout and CSS, browser \code{confirm()} dialogs, the
        Bash scripts, the \code{seed} command, and performance (measured separately with
        \code{cProfile}, see the project report). These are covered by the manual checklist in
        Section~\ref{sec:manual}.
\end{description}

\subsection{Approach}

\paragraph{Level.} Mostly \emph{functional} tests through Flask's test client, which sends real
HTTP requests to the application without starting a server, so each test exercises routing,
login, validation, SQL and templates together. A few \emph{unit} tests call plain functions
(\code{find_clash}, \code{percent}, the report functions) directly.

\paragraph{Isolation.} The \code{app} fixture creates a new application for \emph{every} test with
its database in pytest's per-test temporary folder, and runs \code{sql/schema.sql} on it. Tests can
never see each other's data or touch \code{instance/campus.db}.

\paragraph{Assertions on outcomes.} Tests check both what the user sees (status code, redirect
target, flash message text) and what is stored (a direct SQL query afterwards). A refused action
must leave the row count unchanged.

\paragraph{Exact expected values.} Report tests compare against hand-calculated numbers. They
check \emph{what} is computed, not \emph{how}, so they passed unchanged before and after the
optimisation.

\section{Known limitations and future tests}

\begin{itemize}
  \item \textbf{Concurrency.} Two simultaneous registrations for the last seat are not tested (the
        check and insert are separate statements). A future test could run two registrations in
        threads after the registration is made atomic.
  \item \textbf{Time-dependent data.} Fixtures place events relative to \emph{now}, so tests are
        stable on any date, but a run crossing midnight in the exact second an event starts is
        theoretically possible.
  \item \textbf{Browser tests.} No end-to-end browser automation (e.g.\ Playwright); layout is
        checked manually.
  \item \textbf{Performance} is not asserted in tests; it is measured with \code{profile.sh} and
        recorded in \code{profiling/RESULTS.md}.
\end{itemize}
